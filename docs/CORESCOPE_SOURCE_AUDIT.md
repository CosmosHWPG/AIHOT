## 为什么没有达到 AIHOT 线上的效果

1. **采集覆盖未随目录数量扩大。** 161 个启用来源依赖 V2 产出；CoreScope 目前只有 13 个来源自主抓取。V2 的官网解析、公众号 CLI 等规则没有因为目录导入而迁入。
2. **开源示例不等于线上信源名单。** [上游 README](https://github.com/KKKKhazix/AIHOT#说在前面) 明确说明只提供 18 个公开海外示范来源，不包含 AIHOT 自己的信源名单和运营数据。复用引擎仍需接入真实采集依赖。
3. **网络连接失败减少输入。** Hugging Face、Mistral、Import AI 在实际 `guardedFetch` 客户端中发生连接超时；另一条使用执行环境代理的直连探测能返回有效 RSS。当前证据指向采集客户端的出口差异，不能据此认定源站失效。没有在本次审计中修改代理配置。
4. **分析吞吐受预算限制。** LLM 上限为每分钟 20 次、每小时 180 次、滚动 24 小时 800 次请求。预筛、两次评分、写作与归组会分别调用模型；800 次请求不等于 800 篇新闻，过午夜也不会立即重置。预算与失败重试都由付费回执层管理。02:45 复核时，最近 24 小时已有 720 次 LLM 回执，均收到响应、没有重试；其中评分 253 次、预筛 155 次、结构提取 127 次，其余用于摘要、理解、归组、综述等。停机期间旧请求逐步退出窗口，因此“36 条保留预算错误”不表示复核时额度仍完全耗尽。恢复 worker 后可以继续按原预算处理，没有人为调高额度。
5. **入库、公开和精选是不同阶段。** 首页分层门槛为 T1 60、T1.5 65、T2 76；全部新闻也需要通过公开条件。热点要求最近 48 小时内同事件有至少两个独立参与主体，重复抓取或同机构多个入口不会增加主体数。来源数量增加不必然增加精选或热点。
6. **连续运行曾中断。** 用户确认关闭过启动窗口；之后网页、API、worker、bridge 和 PostgreSQL 均不在运行，未找到主动 Stop 记录。这一启动生命周期问题单独修复，修复结果与验收边界见 `CORESCOPE_STARTUP_FIX.md`。

本次没有同素材的人工作业或模型对照评测，不能把这些运行证据解释为行业分析质量本身不如 AIHOT。

## 补齐采集能力的路径

161 个桥接来源中发现 70 个不带显式凭据的 HTTP feed 候选、4 个 HTTP RSSHub 入口、85 个没有 feed 的来源，另有 2 个需要单独处理的凭据或托管订阅入口。70 个候选尚未验证为 70 个可用 RSS。没有 feed 的来源中，56 个使用 V2 的 `wx biz-articles` 公众号采集；CoreScope 原生公众号适配器使用 Dajiala，不能只改来源类型就复用。

优先验证公开 RSS/Atom 的 XML、日期与网络可达性，再补官网列表 / JSON API 适配；公众号和 X 按各自接口依赖接入。迁移时保留稳定来源身份及管理员停用状态，每个入口明确采用原生采集或桥接，继续只读 V2。不能直接导入带初始化和数据库行为的 V2 `app.py` / Store 模块。

验收应按有效抓取率、最近 24 小时新增、等待分析时长、公开转化、精选转化与热点多主体覆盖衡量。上述来源迁移是后续工作，本次没有通过降低精选门槛或提高付费预算来制造产出。
